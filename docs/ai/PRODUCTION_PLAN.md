## Phase 0 — Stabilize the WIP (do first; unblocks everything)

> **Owner decision 2026-09-23 (scope of the WIP):**
> - **Remove the in-app password manager / credentials vault** (credentials.html, credentials-renderer.js, credentials-crypto.js, credentials-vault-crypto.js, credentials-ipc.js, autofill, `credentials`/`credentials_fts` usage). Instead, point users at an **encrypted note** for storing secrets (notes CN02 encryption stays).
> - **Keep the Profile Gate login screen, simplified to a single profile** with a password prompt (profile-gate.html/renderer, profile-gate-window, profile-session, vault-session-service kept but reduced to one profile; drop multi-profile switching UI).
> - **Remove traffic-log encryption** (traffic-log-crypto.js and the `*_enc`/`log_encrypted` write/read paths). This also deletes the whole "encrypted rows lose headers on export" bug class (A-023 and the HAR/bundle/editor/session-copy data-loss findings become moot).
> - Dead-code cleanup (electron-app/app.js, legacy ffi-napi worker, repo junk): **deferred** for now.
>
> This is a large, WIP-entangled refactor; do it as its own focused effort (separate commits), not mixed with the non-WIP bug fixes. When it lands, the password prompt still protects note decryption and proxy-secret access; the single gate replaces per-profile vaults.

The uncommitted refactor left the app in a broken intermediate state. These are correctness/security regressions, not new features.

1. **Restore the in-tab pages the preload split broke.** Settings (and any other internal page loaded as a tab) lost its APIs when they were removed from `preload-view.js`. Either (a) route internal pages (`settings.html`, `new-tab.html`, etc.) through a dedicated internal preload that keeps the needed APIs and is gated to `file:` internal URLs, or (b) open Settings as a shell `BrowserWindow` with `preload.js` instead of as a tab. See AUDIT `settings`/`ipc-contract` findings.
2. **Close the tab-preload privilege leak (critical).** `preload-view.js` still exposes real-IP, proxy, ext-proxy and full-cookie IPC to every website in a tab. Gate each privileged channel with the trusted-sender guard, and for the few legitimately tab-callable channels (e.g. `new-tab.html` needs IP/proxy status) check `event.sender` URL is an internal `file:` page. See critical cluster.
3. **Fix the vault key-migration data-loss set (critical).** CV01→CV02 verify-blob upgrade must not change the session key mid-session; legacy CV01 fields must stay decryptable/be migrated before the password is dropped; `profile-complete-setup` must not overwrite an existing vault's verify blob without the old master password; `credentials-change-master` must re-key **all** encrypted columns atomically. Add a regression test that unlocks, writes, migrates, and reads back.
4. **Fix encrypted-row export/consumption.** Hydrate encrypted headers/bodies (and normalize header shape: hydrated rows are objects, but HAR/bundle/replay/editor JSON.parse them as strings) before HAR export, bundle export, "session from selection", request-editor prefill, and the redact fallback. See `data-logging`/`log-viewer` findings.
5. **Replace `window.prompt()` everywhere** (Electron has no prompt): request editor, cookie manager, credentials export/switch/delete/folder. One shared `<dialog>`-based `askText()` helper. See A-048.

### Electron/Chromium upgrade cadence (policy, 2026-09-25)

Measured 2026-09-25: Electron **44.4.5** (= Chromium **152**, `process.versions.chrome`) is the latest
Electron release; Chrome stable is **155** (Google versionhistory API); identity templates claim Chrome
**154**. Electron ships a major every ~8 weeks (+2 Chromium majors each) and supports the last 3 majors.

- **Check monthly** (first working day): `npm view electron dist-tags.latest` and
  `curl -s 'https://versionhistory.googleapis.com/v1/chrome/platforms/mac/channels/stable/versions?pageSize=1'`.
  Record both numbers in the progress log below.
- **Adopt every new Electron major within 4 weeks** of its stable release. That keeps the engine at most
  ~3 Chromium majors behind Chrome stable and inside Electron's support window. Patch/minor bumps of the
  current major go in immediately after `npm run test:unit && npm run test:go`.
- **Refresh identity templates with every Electron bump** (`browser-identity-catalog.js` VERSIONS +
  `azuretls-go/profiles.go`; the catalog unit test guards they match). The Chrome template major must be
  ≤ current Chrome stable (never a version that is not released yet). Engine mode needs no change — its UA
  and 2-brand hints derive from `process.versions.chrome`.
- **Gate for a major bump:** `npm run test:unit`, `npm run test:go`, e2e `identity`, `proxy-manager-ui`,
  `site-smoke`, `test:e2e:smoke`; re-check `--use-mock-keychain` (safeStorage), native modules
  (`better-sqlite3` is N-API — no rebuild), and Electron's breaking-changes page for the new major.
- **TLS preset:** the `chrome` profile's ClientHello is our own `chromeClientHelloSpec`
  (`azuretls-go/profiles.go`, Chrome 153 shape: trust-anchor-IDs 51764 payload + ML-DSA sigalgs; see
  `BROWSER_IDENTITY_STATUS.md` §4 (2)). After each Chrome/Electron bump: re-capture the 51764 payload and
  sigalg order from the new Chrome (raw ClientHello capture or tls.peet.ws), update the constants + the
  expectations in `profiles_clienthello_test.go`, run `npm run test:go` and
  `node scripts/tls-fingerprint-compare.mjs` (worker vs headless local Chrome, no window) until
  `JA4 equal true`, then `npm run build:go`.
